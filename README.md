# 🏡 청약알리미 (ChungyakManager)

> **바쁜 하루 속에서도, 중요한 청약 정보만큼은 놓치고 싶지 않았다.**  
> 결혼을 준비하면서 직접 집과 청약 정보를 챙기던 경험에서 시작한 개인 프로젝트입니다.

---

## 💛 왜 만들었을까?

결혼을 준비하면서 역할을 나누어 여러 가지를 챙기고 있었고,  
그중 **집과 청약·임대 관련 정보는 내가 직접 확인하고 관리하기로 했다.**

그런데 실제로 해보니 생각보다 반복되는 일이 많았다.

- 행복주택 / 예비신혼부부 / 공공임대 공고를 매일 직접 확인해야 했고
- 공고가 바뀌었는지 매번 들어가서 비교해야 했으며
- 마감일, 발표일, 계약일을 따로 기록해두지 않으면 놓치기 쉬웠고
- 일정이 변경되면 다시 확인해야 했고
- 업무와 결혼 준비를 병행하면서 이 과정을 계속 반복하는 게 번거로웠다

그러다 문득 이런 생각이 들었다.

> **“그냥 내가 자동으로 확인해주는 프로그램을 만들면 안 되나?”**  
> **“내가 일하고 있을 때도 알아서 확인하고, 필요한 것만 알려주면 되지 않을까?”**

그 생각이 바로 **청약알리미의 시작**이다.

처음부터 상업적인 서비스를 만들기 위한 프로젝트는 아니었다.  
실제로 내가 집을 찾는 과정에서 반복되는 일을 줄이고, 중요한 공고와 일정을 놓치지 않기 위해 만든 도구다.

그리고 이 프로젝트는 단순히 만들어보는 데서 끝나지 않았다.  
**실제로 청약알리미를 이용해 공고를 확인하고 관리했고, 그 과정에서 지금 살고 있는 집을 구하게 되었다.**

내가 겪던 문제를 해결하기 위해 만든 프로그램이 실제 생활의 결과로 이어졌다는 점에서 가장 의미 있는 프로젝트 중 하나다.

## 🎯 이 앱이 해결하는 문제

- 매일 공고 사이트를 직접 찾아보는 반복 작업
- 신규 공고를 놓칠 가능성
- 마감일·발표일 등 주요 일정 관리의 번거로움
- 공고 내용이나 일정이 변경됐을 때 다시 확인해야 하는 문제
- 관심 있는 공고와 일반 공고를 따로 관리하기 어려운 점

즉,  
**사람이 반복해서 확인하고 기록하던 작업을 시스템이 대신 수행하도록 만드는 것**이 이 앱의 목표다.

## 🧩 문제 해결 전략

청약알리미는 단순히 정보를 보여주는 앱이 아니라,  
**반복되고 실수하기 쉬운 행동을 시스템으로 대체하는 것**에 초점을 두고 설계했다.

### 1️⃣ 사람이 하던 “매일 확인”을 시스템으로 대체

- API 서버에서 **1시간마다 스케줄러를 실행**해 외부 API 데이터를 수집
- 기존 데이터와 비교해 DB를 자동으로 동기화
- 사람이 직접 사이트를 확인하지 않아도 같은 기준으로 반복 수행

→ 확인 주체를 **사람 → 프로그램**으로 전환

### 2️⃣ 변경 여부를 감이 아닌 데이터 비교로 판단

- 기존 DB 데이터와 신규 수집 데이터를 비교
- 신규 / 일정 변경 / 상태 변경을 기준에 따라 판별

→ 느낌이 아니라 **데이터 차이로 판단**

### 3️⃣ 놓치기 쉬운 마감을 자동 처리

- 공고 종료일을 기준으로 마감 대상을 확인
- 종료된 공고의 상태를 자동 갱신
- 서버 시간대 차이로 발생한 마감 누락 문제까지 보완

→ 사람이 나중에 정리하던 작업까지 자동화

### 4️⃣ 기다려서 확인 → 필요한 것만 알림 받기

- 관심 공고를 즐겨찾기로 관리
- 즐겨찾기 데이터를 알림 대상과 연결
- 주기적으로 알림 대상을 확인해 Slack 메시지 발송
- 발송 이력을 별도 로그로 저장하고 화면에서 조회

→ 직접 확인하는 방식에서 **필요한 정보를 전달받는 방식**으로 전환

### 5️⃣ 무료 클라우드의 제약을 운영 구조 개선으로 해결

초기 API 서버는 **Azure App Service 무료 환경**에서 운영했다.

무료 환경에서는 일정 시간 호출이 없으면 애플리케이션이 휴면 상태로 전환되어,  
정해진 시간에 스케줄 API를 호출하더라도 서버가 바로 응답하지 못하는 문제가 있었다.

반대로 휴면을 방지하기 위해 지나치게 자주 요청을 보내는 방식은 무료 운영의 취지와 맞지 않았고, 사용량에 따른 비용 부담 가능성도 있었다.

그래서 **GitHub Actions**를 이용해 실제 스케줄 실행 전에 먼저 `wake-up` 요청을 보내 서버를 깨우고,  
몇 초 후 실제 스케줄 API를 호출하는 방식으로 보완했다.

하지만 GitHub Actions의 scheduled workflow는 항상 정확한 정각 실행을 보장하지 않아,  
알림과 데이터 동기화처럼 시간에 민감한 작업을 안정적으로 운영하기에는 한계가 있었다.

결국 사용하지 않던 노트북을 **홈서버로 개량**하고,  
ASP.NET Core API를 **Docker 컨테이너**로 올려 직접 운영하는 구조로 변경했다.

현재는 API 서버 내부에서 스케줄러가 **1시간마다 직접 실행**되도록 구성해,  
외부 스케줄러의 실행 시각이나 클라우드 휴면 상태에 의존하지 않도록 운영하고 있다.

→ 단순한 우회에서 끝내지 않고, 실제 운영 문제를 기준으로 **스케줄링 구조 자체를 개선**

## 🏗️ 동작 구조

```text
                    ┌────────────────────────────┐
                    │   Home Server / Docker     │
                    │      SeinServices.Api      │
                    │                            │
                    │  Internal Scheduler        │
                    │      every 1 hour          │
                    └─────────────┬──────────────┘
                                  │
                                  ▼
                         공공주택 Open API
                                  │
                                  ▼
                         공고 수집 / DB 동기화
                                  │
             ┌────────────────────┼────────────────────┐
             │                    │                    │
             ▼                    ▼                    ▼
       마감 자동 처리       알림 대상 확인        Schedule Log
                                  │
                                  ▼
                              Slack 발송
                                  │
                                  ▼
                              Alarm Log
                                  │
                                  ▼
                              Database
                                  │
                                  ▼
                       Chungyak Manager Web
                    Dashboard / Search / Detail
                       Favorite / Logs
```

프론트엔드는 Vercel에서 서비스하고,  
백엔드는 홈서버의 Docker 환경에서 별도로 운영한다.

## 🔍 개발하면서 해결한 문제

### API 연동 전환

초기에는 mock 데이터를 이용해 화면 구조와 사용자 흐름을 먼저 설계했다.  
이후 실제 API 연동으로 전환하면서 대시보드, 조회, 상세, 즐겨찾기, 로그 화면을 실제 데이터 기준으로 동작하도록 변경했다.

### 스케줄 실행 상태 확인

자동화는 화면에서 바로 보이지 않기 때문에, 단순히 스케줄만 실행하는 구조로 두면 정상 동작 여부를 확인하기 어려웠다.

그래서 최근 동기화 시간과 실행 결과를 로그로 저장하고,  
프론트에서도 스케줄 로그를 조회할 수 있도록 구성했다.

### Azure 무료 환경의 휴면 문제와 스케줄링 구조 변경

처음에는 Azure App Service의 무료 환경을 이용해 API 서버를 운영했다.

하지만 일정 시간 요청이 없으면 서버가 휴면 상태로 전환되기 때문에,  
스케줄 시간이 되었을 때 첫 요청이 서버를 깨우는 데 사용되어 실제 작업이 원하는 시점에 실행되지 않는 문제가 있었다.

이를 해결하기 위해 GitHub Actions에서

`wake-up 요청 → 몇 초 대기 → 실제 스케줄 API 호출`

순서로 실행하도록 구성했다.

이 방식으로 Azure의 휴면 문제는 우회할 수 있었지만, 이후에는 **GitHub Actions 스케줄 자체가 정각에 정확하게 실행되지 않을 수 있다는 문제**가 남았다.

스케줄 실행 시간을 더 안정적으로 관리하기 위해 사용하지 않던 노트북을 홈서버로 구성하고,  
API 서버를 Docker로 배포한 뒤 **애플리케이션 내부 스케줄러가 1시간마다 직접 작업을 실행하는 구조**로 변경했다.

결과적으로 운영 구조는 다음과 같이 변화했다.

`Azure Free + GitHub Actions Scheduler`  
`→ GitHub Actions Wake-up + Schedule 호출`  
`→ Home Server + Docker + In-process Scheduler`

### UTC / KST 시간 차이

자동 마감 처리 과정에서 서버의 UTC 기준 시간과 한국 시간의 차이 때문에 일부 공고가 예상한 시점에 마감되지 않는 문제가 있었다.

시간 기준을 명확히 나누고 처리 로직을 수정해 자동 마감이 정상적으로 동작하도록 보완했다.

### 알림 기능 확장

단순 Slack Webhook 호출에서 끝내지 않고,

`즐겨찾기 → 알림 대상 생성 → 주기 조회 → Slack 발송 → 발송 로그 저장`

흐름으로 분리해 알림 이력을 확인할 수 있도록 구성했다.

## ✨ 마무리

이 프로젝트는 처음부터 거창한 서비스를 만들기 위해 시작한 프로젝트가 아니다.

**직접 집을 찾는 과정에서 반복되는 불편을 줄이고,  
중요한 청약 정보를 놓치지 않기 위해 만든 도구**다.

그 과정에서 단순 화면 구현을 넘어  
공고 수집, 데이터 비교, 자동 마감, 즐겨찾기, 알림, 로그까지 하나의 흐름으로 연결하게 됐다.

그리고 가장 중요한 결과는,  
**이 프로젝트를 실제로 사용해 지금 살고 있는 집을 구했다는 것**이다.

결국 시작점은 단순했다.

> **“매일 내가 확인하지 않아도, 필요한 정보는 알아서 챙겨주는 프로그램을 만들자.”**
